# Einzig

> **一个主题，只有一个权威。**&#8203;
> 「为了不影响全体」——冲突项先隔离、登记，经用户批准后才重新并入连结体。

Einzig 是一套让 Agent 迭代 Obsidian 文档的工作流与治理规则。它不合并原文：
每份用户输入保留原样，迭代只产出「沿用 / 被替代 / 冲突待确认」差异表与来源双链；
冲突项隔离登记，不擅自判定；只有经用户批准的结论才写进该版本的权威分册。
人类读一屏精简层，Agent 按需展开折叠的细节层。

**迭代 ≠ 覆盖。迭代 = 版本链 + 差异表 + 冲突清单。**&#8203;

## 安装

Einzig 0.1.0 面向桌面 Obsidian 1.10 或以上。解压发布包，将 `einzig` 文件夹放进目标 Vault 的 `.obsidian/plugins/`，在「设置 → 第三方插件」启用 Einzig。要看统一修改表，请同时启用核心插件 Bases。

从源码安装时，在本项目执行以下命令。安装脚本只复制插件产物，安装后在 Obsidian 内启用。

```powershell
npm run build
npm run install:vault -- "F:\path\to\vault"
```

## 接入工作区

安装脚本会把 Agent 协作 skill 放到 Vault 的 `skills/einzig-doc-governance/SKILL.md`。手动解压安装时，从安装包复制同名文件夹到 Vault 的 `skills/`。在 Vault 根目录 `AGENTS.md` 加一条链接，提示 Agent 处理设计文档时先读该 skill 和项目规则。如果 Agent 没有自动读到该入口，在任务开头把 Vault 路径和 `AGENTS.md` 路径交给它。

1. 运行「Einzig: 初始化或配置工作区」。预览现有路径和需要新建的目录，然后点「应用工作区」。
2. MINISQUAD 可使用默认映射，用户继续自由写入 `用户输入/待整理`。玩法、进行中、工程和归档位于各自的 `版本/Vx` 下，共享工程位于 `共享工程`。启用后的玩法直接编辑会登记为检测到的变更，作者标为未知。
3. 在文件列表右键文件夹，设置颜色或上锁。颜色可在子目录覆盖，锁覆盖后代目录。锁防止 Obsidian 内误编辑，并约束 Einzig 自身写入。可在 Einzig 设置中暂停目录锁，保留锁列表。其他进程仍有各自的文件系统权限。
4. 运行「Einzig: 巡检文档格式和权威冲突」查看未纳管笔记、格式错误和重复权威。

## 需求演进

1. 打开一篇相关笔记，运行「Einzig: 生成 Agent 整理请求」，指定版本、功能 Key、功能链路、适用模式和标签。主题已有旧玩法页时，可以选它作为纳管目标。选择关联来源后，将生成的请求交给你正在使用的 Agent。
2. 运行「Einzig: 导入 Agent 提案」，粘贴 Agent 返回的 JSON。插件校验原文引句和文件指纹，然后更新该功能的演进草稿。重复导入同一提案会复用草稿。
3. 打开草稿，运行「Einzig: 审核当前需求演进草稿」。逐条勾选准备批准的变化，预览后确认。冲突可以留在草稿中，独立提交解决条款供审核。审核期间如果来源或目标发生变化，需要重新生成预览。
4. 运行「Einzig: 打开统一修改记录表」，按日期、版本和功能 Key 查看修改、来源、批准状态和执行结果。Git 历史可以与这份记录配合使用。发生中断时，运行「Einzig: 核对中断的审批写入」核对当前文件并补齐记录。

功能 Key 由你为主题指定，例如 `MS-F0042`。功能链路用于阅读和搜索，例如 `MINISQUAD-战场-出生点-部署点`。Einzig 用固定算法从文档类型、版本和功能 Key 生成新文档 ID，从文档身份、审核基线和获批正文生成修改 Key。同样的审核输入会得到同样的 Key。修改记录用变更摘要命名，Key 保存在 YAML 属性中。创建与更新日期、标签、适用范围和来源双链也写入 YAML 属性。草稿里长条款证据默认折叠。

Einzig 首版在生成整理请求时查找候选来源。整理请求包含你选中的笔记文本，由你决定交给哪个 Agent。原始输入仍在原目录，可按项目规则核对后手动迁入已处理。

## 开发

```powershell
npm test
npm run build
```

构建产物位于 `dist/einzig`，包括 `manifest.json`、`main.js` 和 `styles.css`。
